# Persian Corporate Copy & UI Polish

این Skill برای پروژه `C:\Users\Asus\Desktop\site` ساخته شده است. هدف آن بازنویسی و بهبود سایت شرکتی فارسی «نقش و هنر مهرسام» است، بدون بازطراحی کامل و بدون افزودن React، Tailwind، shadcn، TypeScript یا کتابخانه خارجی.

از این Skill وقتی استفاده کن که کاربر می‌خواهد متن، تیتر، CTA، توضیحات خدمات، خوانایی، humanizing، typography، spacing یا polish محدود UI/UX سایت شرکتی فارسی بهتر شود.

## 1. محدوده مجاز

مجاز است:

- بازنویسی متن‌های visible در `index.html` پس از گزارش و تأیید.
- پیشنهاد تیترها، CTAها، توضیحات خدمات و microcopy فارسی.
- اصلاح محدود تایپوگرافی، spacing، line-height، max-width، focus/hover/active states در `assets/css/style.css` پس از گزارش و تأیید.
- حفظ ساختار HTML/CSS/Vanilla JS فعلی.
- استفاده از اطلاعات واقعی موجود در سایت: نام شرکت، سال تأسیس ۱۳۹۶، حوزه‌های معماری، عمران، برق، مکانیک، آدرس و شماره‌های موجود.

مجاز نیست:

- نصب یا اضافه کردن React، Tailwind، shadcn، TypeScript، Bootstrap یا هر dependency جدید.
- clone یا کپی کورکورانه ریپوهای خارجی.
- اضافه کردن پروژه، مشتری، لوگو، testimonial، آمار، مجوز، رتبه یا ادعای جعلی.
- استفاده از لینک `#` برای اقدام واقعی.
- بازطراحی کامل layout، تغییر هویت بصری اصلی یا مهاجرت تکنولوژی.
- افزودن تصویر placeholder خارجی، stock photo، لوگوی شرکت‌های دیگر یا داده ساختگی برای social proof.

## 2. لحن برند

لحن مطلوب:

- رسمی، انسانی، مهندسی و قابل اعتماد.
- دقیق و بی‌اغراق.
- روشن و قابل فهم برای کارفرما، نه فقط متخصص فنی.
- فارسی روان با جمله‌های کوتاه و متوسط.
- بدون شعارهای کلیشه‌ای و بدون ادبیات تبلیغاتی پر سر و صدا.

از این‌ها پرهیز کن:

- «ارتقای تجربه»، «راهکارهای نوآورانه»، «کیفیت بی‌نظیر»، «متعهد به تعالی»، «پیشرو»، «تحول‌آفرین»، «بی‌رقیب»، «در دنیای امروز».
- ادعاهای بدون پشتوانه مثل «مورد اعتماد صدها مشتری»، «بهترین شرکت»، «ده‌ها پروژه موفق» مگر داده واقعی وجود داشته باشد.
- سه‌تایی‌های مصنوعی و تکراری، جمله‌های خیلی یکدست، نتیجه‌گیری‌های کلی و upbeat.
- علامت تعجب، emoji و تیترهای بیش از حد نمایشی.

## 3. فرایند بازنویسی متن

برای هر بخش این ترتیب را رعایت کن:

1. هدف بخش را مشخص کن: معرفی، اعتمادسازی، توضیح خدمت، هدایت به تماس یا رفع ابهام.
2. متن فعلی را از نظر وضوح، صداقت، تکرار و حس AI-generated بررسی کن.
3. اگر ادعایی نیاز به سند دارد و سندی در پروژه نیست، آن را حذف یا نرم‌تر کن.
4. جمله را از سمت مخاطب بنویس: کارفرما چه می‌فهمد، چه تصمیمی می‌گیرد، چه ابهامی کمتر می‌شود؟
5. خروجی را با صدای بلند تصور کن. اگر شبیه بروشور عمومی یا متن هوش مصنوعی بود، دوباره کوتاه‌تر و مشخص‌تر بنویس.

## 4. قواعد تیتر و زیرتیتر

تیتر خوب برای این سایت باید:

- پیام اصلی را مستقیم بگوید.
- با حوزه واقعی شرکت هماهنگ باشد.
- از کلمات مهندسی قابل فهم استفاده کند.
- در دسکتاپ و موبایل قابل خواندن بماند.

الگوهای مناسب:

- «طراحی و نظارت ساختمان با هماهنگی بین رشته‌های مهندسی»
- «از بررسی اولیه تا تحویل نقشه‌های قابل اجرا»
- «طراحی معماری، سازه و تأسیسات در یک مسیر هماهنگ»
- «مشاوره مهندسی برای تصمیم‌های دقیق‌تر در پروژه ساختمانی»

الگوهای نامناسب:

- «خلق آینده‌ای نوین در صنعت ساختمان»
- «راهکارهای جامع و بی‌نظیر برای تمامی نیازهای شما»
- «تجربه‌ای متفاوت از طراحی و اجرا»

## 5. قواعد CTA

CTA باید دقیقاً بگوید کاربر چه کاری می‌کند یا چه چیزی می‌گیرد.

CTAهای مناسب برای این سایت:

- «درخواست مشاوره»
- «تماس برای هماهنگی جلسه»
- «مشاهده خدمات مهندسی»
- «بررسی روند همکاری»
- «ارسال پیام در واتساپ»

CTAهای ضعیف یا مبهم:

- «شروع کنید»
- «بیشتر بدانید»
- «کلیک کنید»
- «ارسال» بدون زمینه

قواعد:

- برای یک intent، یک عبارت ثابت استفاده کن. مثلاً اگر intent تماس است، بین «تماس»، «ارتباط»، «شروع همکاری» و «درخواست مشاوره» مدام جابه‌جا نشو.
- CTA اصلی معمولاً تماس یا درخواست مشاوره است.
- CTA ثانویه معمولاً مشاهده خدمات یا روند همکاری است.
- هیچ CTA بدون مقصد واقعی نساز.

## 6. توضیحات خدمات

هر توضیح خدمت باید این سه چیز را روشن کند:

1. خدمت چیست.
2. در پروژه ساختمانی به چه تصمیم یا خروجی کمک می‌کند.
3. چه ارتباطی با سایر رشته‌ها یا اجرا دارد.

بدون سند واقعی، نتیجه کمی نساز. ننویس «کاهش ۴۰٪ خطا» یا «صرفه‌جویی قطعی در هزینه».

نمونه سبک مناسب:

> طراحی تأسیسات مکانیکی با توجه به نیاز پروژه، مسیرهای اجرایی، هماهنگی با معماری و الزامات بهره‌برداری انجام می‌شود.

نمونه سبک نامناسب:

> ما با بهره‌گیری از راهکارهای نوین، بهترین و کامل‌ترین خدمات تأسیسات مکانیکی را ارائه می‌دهیم.

## 7. Humanizing و ضد AI-slop

قبل از ارائه متن نهایی، این موارد را حذف یا اصلاح کن:

- کلی‌گویی بدون مثال یا زمینه.
- صفت‌های زیاد به جای اسم و فعل دقیق.
- ساختارهای «نه فقط... بلکه...» وقتی واقعاً لازم نیست.
- عبارت‌های نمایشی مثل «در قلب»، «گامی مهم»، «نقشی کلیدی»، «چشم‌انداز آینده».
- جمله‌های هم‌اندازه و هم‌ریتم پشت سر هم.
- نتیجه‌گیری‌های عمومی مثل «آینده روشن است».

برای انسانی‌تر شدن:

- گاهی جمله کوتاه بنویس.
- از فعل‌های ساده استفاده کن: «بررسی می‌کنیم»، «هماهنگ می‌شود»، «تحویل می‌دهیم».
- محدودیت را صادقانه بیان کن. برای بخش پروژه‌ها، اگر سند و تصویر آماده نیست، شفاف و کم‌حرف بگو.
- از کلمات آشنا در کار مهندسی استفاده کن: نقشه، محاسبات، کنترل، هماهنگی، اجرا، ضوابط، مدارک، بازبینی.

## 8. اعتمادسازی واقعی

اعتماد در این پروژه از مسیر ادعای بزرگ ساخته نمی‌شود؛ از وضوح، اطلاعات واقعی و پرهیز از اغراق ساخته می‌شود.

موارد قابل استفاده:

- سال تأسیس ۱۳۹۶.
- حوزه‌های معماری، عمران، برق و مکانیک.
- خدمات اصلی موجود در سایت.
- آدرس و شماره تماس واقعی.
- ساعت کاری موجود.
- توضیح شفاف درباره اینکه پروژه‌ها پس از آماده شدن مستندات واقعی منتشر می‌شوند.

موارد غیرمجاز:

- نام مشتریان یا پروژه‌های ساخته‌شده.
- تعداد پروژه‌ها، درصد موفقیت، رتبه، مجوز یا testimonial بدون سند.
- لوگوی سازمان‌ها یا شرکت‌ها بدون اجازه و داده واقعی.

## 9. UI/UX و typography polish محدود

پیش از هر تغییر CSS، فایل‌های `index.html` و `assets/css/style.css` را بخوان.

اولویت اصلاح با کمترین ریسک:

1. خوانایی متن فارسی: line-height، max-width، text-wrap، فاصله پاراگراف‌ها.
2. hierarchy تیترها: h1/h2/h3 واضح، نه شلوغ و نه خیلی کوچک.
3. spacing بین سکشن‌ها و داخل کارت‌ها.
4. CTA states: hover، active، focus-visible و حداقل ارتفاع لمس.
5. کاهش تکرار بصری: eyebrow زیاد، کارت‌های کاملاً مشابه، فاصله‌های یکنواخت.
6. کنتراست در dark/light.

قواعد اجرایی:

- از CSS variables موجود استفاده کن.
- `transition: all` اضافه نکن؛ property مشخص کن.
- motion را محدود نگه دار و `prefers-reduced-motion` را رعایت کن.
- برای متن فارسی `line-height` حدود 1.75 تا 1.95 مناسب است.
- برای headingها `text-wrap: balance` و برای پاراگراف‌ها در صورت پشتیبانی `text-wrap: pretty` مناسب است.
- max-width متن‌های طولانی حدود 60 تا 68ch باشد.
- تغییرات باید کوچک، قابل review و برگشت‌پذیر باشند.

## 10. خروجی قبل از تغییر HTML

قبل از تغییر `index.html`، همیشه گزارش بده:

1. چه متن‌هایی قرار است تغییر کنند.
2. چرا تغییر لازم است.
3. نمونه قبل/بعد برای هر بخش.
4. آیا تغییر شامل ادعای جدید است یا نه. اگر بله، منبع داده چیست؟

فرمت پیشنهادی:

```markdown
### Hero
قبل:
> ...

بعد پیشنهادی:
> ...

دلیل:
- کوتاه‌تر است.
- پیام اصلی را زودتر می‌گوید.
- ادعای جدید اضافه نمی‌کند.
```

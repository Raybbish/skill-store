OH-MY-SKILL · ARCHITECTURE · 2026-07-04

安全扫描 → 可插拔信任服务

把「扫描」从商店的内嵌步骤,变成一个以 content_hash 为锚、以 verdict 为产出的独立判定服务。商店是它的第一个消费方,不是宿主。

状态 设计稿 · 待定稿为 ADR 0012 前置 ADR 0011(扫描已整套下架) 手法对齐 ADR 0007 埋缝不搬家
TL;DR

核心一刀:判定(verdict)从 skill-report.json 里拆出去,锚定 content_hash,自带版本。服务对外只暴露五个接口 + 一个事件;商店在管线、前端、CLI 三处各留一个 optional 插拔点,verdict 缺席时商店完整可用。重新上架 = 打开一个 flag——这就是「可插拔」的验收标准。部署形态分四阶段演进(同仓 package → 独立进程 → 多租户服务 → 生态),契约从第一天冻结。

§0

为什么要拆:这次下架的验尸报告

2026-07-04 下架安全扫描,动了 29 个文件:前端组件、两处页面嵌入、类型定义三层(Skill / SkillCard / idx)、筛选器、CLI 披露、六处文案、构建脚本的 pass 门禁。一个「功能」渗进了每一层,说明它从来不是模块,是弥散状态。

反例就在同一个仓里:取数走 search()/getSkill() 一条缝(ADR 0007),换实现零改动。信任层缺的正是同一条缝。这份设计的目标:下一次上架/下架/换引擎,商店侧改动 ≤ 1 个 flag。

§1

设计原则

  1. 判定是内容的纯函数。
    verdict = scan(content_hash, policy_version)。同输入必同输出 → 天然幂等、可缓存、可复算、可增量重扫。判定对象是内容,不是 skill 名字。
  2. 商店零依赖。
    verdict 是 optional 装饰:服务不在,货架、搜索、安装、评测全部照常。展示 fail-open,门禁 fail-closed。
  3. 契约先行,实现可换。
    冻结 verdict schema 与五个接口;L1/L2/L3/人工是服务内部细节,外部只见状态机。裁决口径是版本化配置,不是散在代码里的 if。
  4. 判定可审计。
    每条 verdict 带证据链、决策链(谁判的:规则/模型/人)、版本号;append-only,公开可验证——和 catalog「事实源走 git 账本」同一哲学。
  5. 先埋缝,后搬家。
    S0 就是同仓一个 package + 独立数据目录,不建新服务不加运维。部署形态跟着规模走,契约不动(P0 手法复用)。
§2

总体架构

上下分离:商店(消费方)── 缝(契约)── 判定服务(生产方)── 数据账本

商店(消费方)
build-index 构建期 join(optional 字段)· TrustBadge 前端开关组件 · CLI 装前披露(optional)—— 三个插拔点,flag 统一控制
▲ 只读 verdict ▲
缝:verdict 契约(冻结)
scan-verdict@v1 schema + submit / getVerdict / batchGet / listQueue / decide + 事件 verdict.updated —— transport 无关:S0 函数调用,S1 起 HTTP
▲ 生产 verdict ▲
判定服务(编排器 + scanner 插件)
L1 静态签名 · L2 数据流五因子 · L3 LLM 意图 · 人工复核队列 —— 层即插件,可增删换序;裁决策略 = 版本化 policy 文件
▲ 读写 ▲
verdict 账本(append-only)
S0:catalog/verdicts/ git 目录(公开可验证)→ S1+:Postgres 主存 + git 导出审计副本 → S3:透明度日志(merkle)

与现有管线的关系:ingest 完成收录后向服务 submit()(异步,不阻塞上架);内容哈希漂移时重新 submit。收录与判定彻底解耦——skill-report.json 里不再有 security_audit,只留 content_hash 锚点。

§3

核心契约

3.1 scan-verdict@v1

{
  "schema": "scan-verdict@v1",
  "subject": { "skill_id": "owner/repo/name", "content_hash": "sha256:…" },  // 锚定内容,不是名字
  "scanner": { "engine": "1.4.0", "policy": "2026.07", "models": ["deepseek-v4", "qwen-max"] },
  "status": "pass | flagged | rejected | pending | error",
  "factors": { "network": {…}, "scripts": {…}, "filesystem": {…}, "env_access": {…}, "external_commands": {…} },
  "evidence": [ { "factor", "file", "line", "note" } ],
  "decisions": [                                          // 决策链,append-only
    { "layer": "L1",    "verdict": "clean",   "at": … },
    { "layer": "L3",    "verdict": "flagged", "by": "deepseek-v4", "note": … },
    { "layer": "human", "verdict": "pass",    "by": "Raybbish", "signature": …, "note": … }
  ],
  "issued_at": …, "supersedes": "sha256:…@2026.05"       // 旧版本判定的指针
}

3.2 状态机

迁移触发说明
pending → pass / flagged自动层(L1→L2→L3)编排器按 policy 合成;任一层 error 则 fail-closed 停在 pending
flagged → pass / rejected人工 decide(带签名)唯一的人工通道;签名留痕进 decisions[]
任意 → pending(新 verdict)content_hash 变化新内容=新 subject;旧 verdict 保留为历史,不覆写
pass → 增量重扫policy_version 升级只重跑受影响因子;旧 verdict 标 superseded

3.3 接口(五个 + 一个事件)

接口语义
submit(subject)幂等入队;同 hash 同 policy 直接返回既有 verdict
getVerdict(hash) / batchGet([...])商店唯一的读入口;构建期批量 join 用 batchGet
listQueue(filter)人工复核队列,按风险分排序,容量可配(~5 条/日)
decide(hash, verdict, sig)人工裁决;必须带签名与 note
事件 verdict.updatedS0 = 回调/轮询;S1+ = webhook。商店据此触发 re-index
Transport 无关是刻意的:S0 阶段这五个接口就是 packages/verdicts 导出的五个函数;S1 起原样映射成 HTTP。签名不变,消费方代码不改。
§4

商店侧:三个插拔点

位置接法服务缺席时
管线 ingest收录完成后异步 submit();哈希漂移重新 submit跳过,收录照常
前端 build-indexbatchGet 后 join 到瘦卡的 optional verdict 字段;TrustBadge 组件仅在字段存在时渲染字段缺省,UI 无痕
CLI add装前披露读 verdict(optional);content_hash 完整性校验与本服务无关,永远在只走确认 + 哈希校验

三处由同一个开关 TRUST_DISPLAY 控制。门禁是另一个开关 TRUST_GATE(rejected 不上架 / 场景包要求 pass),且门禁判断放服务侧提供的谓词里,商店只问「能不能上」,不自己解释 verdict——避免这次 build-index 里 status !== "pass" 这种口径泄漏。

失败模式:展示 fail-open(服务挂 → 没徽章,商店照常);门禁 fail-closed(gate 开着而服务不可用 → 暂停新条目 promotion,存量不动);LLM 失败 → verdict 停 pending,绝不默认放行(沿用旧红线)。
§5

服务内部:层即插件,口径即配置

编排器持有一个 scanner 插件数组,每个插件实现 scan(content) → PartialVerdict(因子 + 证据 + 置信度)。现有三件套原样搬入:rules.ts(L1)、analyze.ts(L2)、llm.ts(L3);「人工」也是一个插件,只是它的 scan 是把条目放进队列等 decide。

裁决策略拆成版本化 policy 文件(什么算重大风险、哪些因子触发 flagged、L3 能否下调 L2、复核容量)——ADR 0011 要研究的正是这份配置的内容,研究迭代发生在 policy 版本号里,不再牵动任何代码。旧口径(L3 最终裁决、仅重大风险转人工、network 非硬红线、fail-closed)作为 policy 草稿 v0 的输入。

这也是 S3 生态的伏笔:第三方 scanner(社区规则包、别家引擎)实现同一插件接口即可接入,decisions[] 里如实记录判定来源。

§6

数据账本演进

阶段主存公开可验证
S0catalog/verdicts/<owner>/<repo>/<name>.json(git)天然:PR 溯源 + commit 历史,与 catalog 哲学一致
S1–S2Postgres(verdicts / decisions / queue 三表,content_hash 主键)定期导出 git 审计副本
S3同上透明度日志:verdict 进 merkle log(CT 式),第三方可证明「判定未被篡改、未被静默撤回」

现存 5,800+ 份 security_audit 历史数据一次性迁成 verdict 格式,scanner.engine = "legacy",只作历史参考,不参与展示与门禁。

§7

部署形态:四阶段(对齐百万级 P0–P3)

S0埋缝
同仓 package,函数调用
packages/verdicts:schema + 五接口 + 编排器 + 三件套搬入;verdict 拆出 skill-report;商店三处 optional 接线,flag off。零新运维。
gate:ADR 0011 研究完成、policy v1 定稿 → 开 TRUST_DISPLAY = 重新上架
S1独立进程
队列 + worker + HTTP
扫描耗时(clone + LLM)开始拖累管线时拆出:轻量队列,worker 横向扩;五接口上 HTTP,商店构建期 batchGet。
gate:目录 >1.5万 或单轮全量扫 >1h 或 LLM 并发需独立限流
S2服务化
独立部署 + 多租户
auth / quota / 计费;oh-my-skill 降级为普通租户;别家目录、企业内部 skill 仓接入——「信任即服务」产品线在这里立项,不在这之前。
gate:出现第二个真实消费方
S3生态
插件规范 + 透明度日志
第三方 scanner 插件规范开放;社区规则包;merkle 透明度日志;跨模型交叉判定市场。
gate:S2 稳定运行 + 有第三方引擎接入意愿
§8

从今天的下架状态到 S0:迁移六步

  1. ADR 0012 定契约:scan-verdict@v1 schema、五接口签名、状态机、两个 flag 语义——本文定稿即 ADR。
  2. 建 packages/verdicts:schema/types + git 账本读写 + 编排器骨架;scanners/ 三件套 + review 队列原样搬入为插件(它们已带 ⛔ 头注,搬家时摘掉)。
  3. 历史数据迁移:security_audit → verdict(legacy 标记);skill-report.json 删 security_audit 字段(schema v2)。
  4. 商店侧接线:build-index optional join + TrustBadge 新组件(读 verdict)+ CLI optional 披露;TRUST_DISPLAY / TRUST_GATE 默认 off——货架外观与今天完全一致。
  5. 研究在服务内迭代:ADR 0011 前置清单(裁决口径、误报率、复核吞吐、徽章语义)全部落在 policy 草稿与插件调参里,商店零改动。
  6. 重新上架 = policy v1 定稿 + 全量重扫 + 打开 TRUST_DISPLAY。验收:这一步的 diff 只有 flag。
§9

红线与开放问题

红线(继承不变):全站不说「保证安全」;徽章语义是「已扫描@版本」的结构化披露,不是背书;人工裁决必须签名留痕;LLM 判定 fail-closed。

留给研究(policy v1 之前必须回答):误报率基线怎么测(需要标注集);L3 最终裁决 vs 只升不降的口径选择;复核吞吐 ~5/日 撑到多大目录规模;徽章视觉上「认证 vs 披露」怎么不误导;多租户后 policy 是否允许租户定制(定制即口径分裂,慎)。

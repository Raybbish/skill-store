Skill Store · 架构决策 · ADR 0006

原作者一键认领

让 skill 的原作者把冷启动时归属为空的 listing 收归己有——改图标、答复社区、拿采用数据。身份无法凭空自证,但既然内容源都在 GitHub,「对源仓库的控制权」可自证,这就是认领的支点。本文给出核心口径、验证阶梯、第一方/聚合源分叉、数据模型与 MVP 边界。

日期 · 2026-07-04 落位 · M1 账号层 状态 · 建议 认证栈 · Supabase Auth · GitHub OAuth 关联 · ADR 0001 · 0002
一句话

身份证明 = 对 skill 源 GitHub 仓库的控制权。认领 = 用 M1 已定的 Supabase GitHub OAuth 登录,拿 login / orgs / repo 权限 自动比对源归属,命中即当场绑定 listing——这才是真正的「一键」。MVP 只焊第一方仓的前两档,直接坐在既有 OAuth 上,零新基建;聚合源与挑战验证随后补,人工永久兜底。

01

核心口径

三条前提,决定后面每一步。
  1. 控制权即证明。 authorship 不可自证;但内容源都在 GitHub,能证明你控制源仓库,就等于证明你是作者。整套设计围绕这一条展开——不去核对「你是不是本人」,只核对「你能不能动这个仓」。
  2. 复用已定的 Auth,不造新轮子。 M1 账号层已定 Supabase Auth(GitHub + 邮箱,ADR 0001)。认领直接坐在它的 GitHub OAuth 上:一次登录即拿到 login、orgs、对源仓的 repo 权限,足够判定归属,零新增身份基建。
  3. 命中即停,越靠前越「一键」。 五档验证按可信度从高到低排,任一命中即绑定、不再往下走。前三档全自动(真·一键),后两档兜底。绝大多数第一方作者在第 1 档就完成。

03

关键分叉:第一方 vs 聚合源

这是和你采集架构强相关的坑——比对逻辑必须按来源分流,否则会把 listing 误绑到搬运工。

三段式 ID owner/repo/name 里的 owner,在第一方仓 = 作者;在聚合 / 精选仓(curated_by 标记、MAX_PER_REPO 折叠来的)= 搬运工。对聚合源套「repo 权限」比对,会把认领权错发给收录它的人。所以先看 source_type,再决定走哪档。

first_party

owner == 作者
  • 走第 1–2 档(repo 权限 / org 成员)即可判定
  • OAuth 拿到 admin/push → 当场自动绑定
  • 覆盖绝大多数条目,MVP 只做这一支

aggregator

owner == 搬运工
  • 跳过第 1–2 档(会误绑搬运工)
  • 只认第 3 档:frontmatter author / 声明源
  • 缺声明 → 落第 4–5 档(挑战 / 人工)

source_type 无需新采集,直接派生自你现有的 curated_by / 折叠信号。

04

认领后授予什么

渐进开放。这些能力是作者愿意来认领的理由,也是它接住 ADR 0002 图标策略的地方。
  • 编辑 listing — 图标(落地 ADR 0002 第 3 档「认领 / 上传覆盖」)、描述覆盖、链接、标签建议。
  • 「作者已验证」身份徽章 — 证实这条 listing 的归属。
  • 答复社区 — ADR 0001 的求助 / 评价互动。
  • 发布者页归属 — packages/web 已有 publisher 页,认领后归属其名下。
  • 后续:采用 / 流量数据 — 认领打通后再开。
红线:身份 ≠ 背书

「作者已验证」只表明归属被证实,不隐含平台对其安全性的担保。徽章须与平台「已扫描 / 已评测」认证视觉与文案分离(沿用 ADR 0002),全站不说「保证安全」。Apache-2.0 §6 不授商标——认领给的是 listing 控制权,不是使用其 logo 的权利;移除请求并入 DMCA / 商标流程。

05

数据模型

挂在 M1 账号层(Supabase Postgres,与 Auth 同库)。claims 表是撤销与仲裁的证据链,必留。
对象 / 字段取值说明
accountsid · github_user_id · github_login · avatar · emailOAuth 落地的账号主体
skills.owner_account_idfk · nullablenull = 未认领(聚合态)
skills.claim_stateenumunclaimed → pending → claimed → verified
skills.source_typeenumfirst_party | aggregator,派生自 curated_by / 折叠
claimsid · skill_id · account_id · method · evidence · status · ts认领审计流:谁、用哪档、凭什么、结果——争议与撤销的唯一依据
 
// 认领判定(命中即返回,前 3 档零人工)
async function resolveClaim(skill, ghUser) {
  if (skill.source_type === "first_party") {
    if (await hasRepoWrite(ghUser, skill.owner, skill.repo)) return "auto:repo";   // 档 1
    if (await inOrg(ghUser, skill.owner)) return "auto:org";                    // 档 2
  } else { // aggregator:跳过 repo 权限,认声明源
    if (declaredAuthor(skill) === ghUser.login) return "auto:frontmatter";      // 档 3
  }
  return needsChallengeOrReview(skill, ghUser);                                     // 档 4 / 5
}
06

增长:静默预填

别让作者去大海里找自己那条 —— 把认领从「主动找上门」变「登录即顺手确认」。
一键全认领

首次 OAuth 后,顺手扫登录者的 repos + orgs,把 catalog 中 owner ∈ {login, orgs} 的 skill 一次性列出:「发现 N 条疑似你的,一键全认领」。这正是 npm / PyPI 登录后自动列出你名下包的套路,认领率会比「一条条搜索认领」高一个量级。

07

防滥用与争议

强路径本身要真控制 GitHub 源,冒领成本已经很高;再补四点堵边角。

① fork 冒领

有人 fork 一份仓就来认领。排除 fork:true 仓作为规范源,只认原始仓;fork 想认领落人工档。

② 权限变更

GitHub 侧 owner / 权限变动(转让、离职)后旧绑定应失效。权限变更触发重验,认领非永久免检。

③ 争议 / 撤销

claims 全程留痕,admin 可撤销 / 仲裁;多方争夺同一条直接进人工档,凭证据链裁决。

④ 刷量

认领限流;因为自动档都要求对源仓的真实控制权,批量冒领无法绕过 GitHub 权限本身。

08

边界:MVP 只做什么

「一键」= 把第一方仓那两档焊对,坐在既有 OAuth 上;不是一次把五档全建齐。

现在别做

  • 挑战验证(档 4)—— 聚合认领有真实需求再补
  • 聚合源 frontmatter 档 —— 同上,依赖 author 字段普及
  • 复杂争议工作流 —— 先 admin 手动兜底
  • 采用数据看板 —— 认领打通后再说
  • 独立认领后台 —— 复用现有 publisher 页

现在就做(M1)

  • Supabase GitHub OAuth 登录 + accounts 表
  • 第 1–2 档自动比对(第一方仓)—— 零新基建
  • owner_account_id + claim_state + claims 三件套
  • 静默预填「一键全认领」
  • 「作者已验证」徽章(与认证徽章分离)

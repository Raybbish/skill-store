Skill Store · 架构决策

走向百万级的
完整架构与迁移计划

从今天的 6k 条静态站,到目录承载几十万乃至上百万 skill。核心不是"把列表渲染快",而是换一套随规模扩展、且不丢掉"可公开审计"信任故事的服务架构。本计划给出不变量、终局架构、四阶段迁移(带触发阈值)与立即行动。

日期 · 2026-07-04 当前规模 · 5,811 可见 / 6,171 条 目标规模 · 10⁵–10⁶ 栈 · Next.js 15 · React 19 状态 · 提案,待落 ADR
一句话

catalog(Git)是唯一事实源与公开审计账本;搜索/浏览是"查询一份派生索引",不是"下载整个目录"。前端只通过 search() 与 getSkill() 两个入口取数,背后从静态 JSON → 托管搜索引擎 → 数据库逐阶段替换,每次都是局部替换而非重写。现在就埋这条缝、直接上搜索引擎当索引;别在 6k 条时建百万基建,但也别再往"把全量塞进浏览器"的死路上走。

01

五条不变量

任何阶段、任何实现都不违反。它们是让"从一万到一百万只换实现、不换架构"成立的前提。
  1. 源与服务分离。 Git catalog 是可 diff、可 PR、可公开复核的记录账本,不是请求路径。用户看到的一切都从派生的、可随时重建的索引/DB 来,索引是 catalog 的纯函数。
  2. 前端只认两个入口。 search(query, filters, page) 与 getSkill(id) 是唯一数据契约。背后是文件、搜索引擎还是数据库,前端一律不知情。这条缝是所有迁移的支点。
  3. 永不把目录下发给客户端,永不全量预渲染。 百万文档的索引几百 MB、百万个 HTML 页 99% 没人看。浏览走搜索 API,详情页按需渲染 + CDN 缓存。
  4. 采集幂等、增量,按 content_hash 去重并缓存审计。 加一条 skill 是 O(1) 增量,不是全量重跑。L3(LLM)只在内容变更时触发,否则百万 × 模型调用成本失控。
  5. 信任靠自动化扩展,人工只碰长尾。 L1/L2/L3 自动审计必须扛住主量,人工每天只看少量重大风险。fail-closed 保留,含可撤销(revocation)。

03

四阶段迁移

每阶段独立可上线,由真实阈值触发进入下一阶,不提前跨。当前该做的是 Phase 0 与 Phase 1。
Phase 0 止血 + 埋缝 现在 · ~6k · 保持静态导出
目标:交互立刻不卡 + 焊死数据契约缝。这是唯一"以后都不会浪费"的阶段,越早越好。
  • 分页取代整表渲染:列表按页取 ~30 条,?page= 进 URL。P0 仍静态,先在加载好的瘦索引上客户端切片;search() 按 page/size 返回,Phase 1 换 Typesense 后自动变服务端分页、前端不改。DOM 只挂当前页 → 免虚拟化。
  • 瘦 payload:browse/page.tsx 只把列表所需字段传给客户端,evidence/l3/review/eval 不下发(6MB→3.3MB),详情页按需取。
  • 搜索解耦:useDeferredValue + debounce 把输入与重渲染分开。
  • 焊缝:定义 SkillStore 接口(search()/getSkill()),当前实现坐在构建期派生的 index.json + 索引库(Orama/MiniSearch)上。前端从此只认接口。
  • 修构建期 O(n²):lib/data.ts 的 getSkill/skillsByLabel 每次 allSkills() 重扫 6k 文件 → 改为只加载一次建内存索引 / 构建期落一个派生文件。
退出标准6k 条浏览/搜索顺滑;前端只调 search()/getSkill();构建不再随条数平方增长。
Phase 1 抽出搜索服务 触发 · ~1–2 万 或需要分面/纠错/相关性
目标:搜索从"浏览器里扫数组"变成"查一个真正的搜索引擎"。前端仍是静态壳。
  • 自托管搜索引擎上线:Typesense(或 Meilisearch),单节点即可。管线在每次部署/提交时把文档灌进索引。
  • 切 search() 实现:客户端 JSON → 搜索引擎 API。浏览获得真·分面(category/tags/风险因子/publisher/license/hosting)+ 打字纠错 + 排序(installs/stars/新鲜度/质量分)。
  • facets 复用你现有 taxonomy:chips → 真 facets;不再前端 filter() 统计。
  • 详情页此阶段仍可 SSG(<~5 万可行),但开始度量构建时长,设阈值告警。
退出标准搜索由服务端支撑;catalog 不再整包下发到客户端;facets 与排序真实可用。
Phase 2 解耦服务层 触发 · ~5–10 万 或 SSG 构建超时 / Git 文件数吃力
目标:让"加一条 skill"是 O(1) 增量;告别全量预渲染与静态导出。
  • 引入 Postgres 服务库 + 对象存储:Loader 从 catalog 派生 DB;大 blob(mirror zip、完整审计报告)入 R2/S3。getSkill() 读 DB,不再读文件系统。
  • 详情页转按需渲染:ISR/SSR + CDN 缓存,永不全量预渲染。此处有意识地退役 output:"export"——"纯静态随处部署"这个值到百万留不住,Git 仅保留为公开账本。
  • 管线转增量:队列驱动,只有 content_hash 变化的 skill 才重审、重索引;审计结果按 hash 缓存。
  • 批量源折叠继续作为规模阀门(你已有 collections 采样折叠的直觉,正确)。
退出标准无任何请求期或构建期全量扫描;新增/更新 skill 走增量;详情页缓存命中稳定。
Phase 3 百万级:发现 · 信任 · 成本 触发 · 10⁵ → 10⁶ · 并行工作流,非严格串行
目标:百万量级下"找得到、信得过、养得起"。这三件比渲染更决定平台成败。
  • 搜索扩展:Typesense 分片/副本;若相关性或向量需求重,评估 OpenSearch/Vespa。上语义/向量搜索——"帮我找能做 X 的 skill",纯关键词不够。
  • 发现与排序:质量分(信号 + 审计 + 热度 + 新鲜度)、duplicate_of 规范化去重、低质/垃圾降权、trending。
  • 规模化信任:全自动审计门,人工仅长尾重大风险;可撤销 + 变更重审 + 投毒/滥用防护 + 溯源 UX。
  • 成本与运维:分级 LLM 审计(便宜模型初筛 → L3 仅在歧义/变更时);按 hash 缓存;索引自动扩缩;SLO/可观测性。
退出标准百万条下亚百毫秒搜索、增量采集、自动化信任、成本有界。
04

数据契约(那条缝)

Phase 0 就把它焊死。前端与数据层之间永远只有这一层薄接口。
// packages/web/lib/store.ts —— 唯一数据入口,背后实现随阶段替换
export interface SkillStore {
  search(q: string, opts: {
    filters?: { category?: string; tags?: string[]; net?: boolean; status?: string };
    sort?: "installs" | "stars" | "relevance" | "fresh";
    page?: number; size?: number;      // 数字分页(浅页 · 可深链 · CDN 缓存)
    cursor?: string;                    // 深翻兜底:search_after,免深 offset
  }): Promise<{
    hits: SkillCard[]; total: number; facets: FacetCounts;
    page: number; pages: number; nextCursor?: string;  // 喂页码器
  }>;

  getSkill(id: string): Promise<SkillDetail | null>;
}

// Phase 0 实现:坐在构建期 index.json + Orama 上(静态,零服务)
// Phase 1 实现:坐在 Typesense 上   —— 只换这个文件,前端不动
// Phase 2 实现:search→Typesense, getSkill→Postgres

// 列表卡片只带展示所需字段(≈ 600B/条),审计详情不进列表
interface SkillCard {
  id; name; description; publisher; category; tags;
  stars; installs; status; net: boolean;   // net = 是否含网络外联
}

关键点:列表文档只带 SkillCard 这些字段;evidence / l3 / review / eval 这类审计重负荷只在 getSkill() 的详情里出现。这一条同时解决了 Phase 0 的 payload 问题和百万级的索引体积问题——索引里每条 skill 只有几百字节。

分页也走这条缝。search() 已带 page/size,返回带 total/pages 喂数字页码器(你截图那种),顺序深翻用 nextCursor(search_after)避开深 offset。P0 仍静态时先在加载好的瘦索引上客户端切片,接口形状不变——Phase 1 换 Typesense 后自动变服务端分页,前端零改动。每页只取 ~30 条,DOM 天然只有 30 行,因此不必再叠虚拟化。

07

百万级的真正硬问题

不是渲染。这四个决定平台成不成——放进 Phase 3,但架构要为它们预留位置。

① 发现与排序

npm 的教训:几百万包里绝大多数是噪声,找得到才是产品。质量信号、热度、新鲜度、规范化去重、语义召回排第一。搜索不是功能,是核心卖点。
过渡口径(自家遥测/评分未就位):货架头条统一 stars(缺失回落 installs→「新」),排序按归一 stars = stars/√repo_skill_count 抑制巨仓,installs 收进详情页;成熟后并入 quality_score。实测覆盖:stars 98.8% · installs 0.8% · 两者零重叠——故不可混排。

② 规模化信任

百万条没法人工审。你的 L1/L2/L3 必须扛住主量,人工只碰长尾重大风险(你 memory 里的裁决口径方向对)。加可撤销、变更重审、投毒/滥用防护。

③ 采集成本与新鲜度

百万 × LLM 审计会烧钱。只在 content_hash 变更时重审,分级模型初筛,结果按 hash 缓存。新鲜度靠增量,不靠全量重跑。

④ Git 的文件天花板

36k 文件 / 682MB 已不轻;百万条是几十 GB、上百万小文件,clone/status/checkout 全爬。远在百万前就得把服务层挪去 DB/对象存储,Git 只留账本与紧凑记录。

08

边界:别建 vs 就做

"一步到位"= 把缝一次焊对,不是把百万基建一次建齐。避免过度工程。

现在别建(6k 条)

  • Postgres / 队列 / 向量库——Phase 2+ 再上
  • k8s / 多节点搜索集群 / 自动扩缩
  • 个性化推荐、排序模型训练
  • 把详情页提前改 SSR(SSG 现在够)
  • 客户端全量索引(Orama 也只作 P0 过渡,别恋战)
  • 虚拟化(有了分页,每页 30 行用不上)

现在就做(不会浪费)

  • 焊 search()/getSkill() 缝——一切迁移的支点
  • 服务端分页 + 瘦 payload——每页 ~30 条,DOM 天然小,省掉虚拟化
  • 修 data.ts 的 O(n²) 重扫——构建期炸弹
  • 直接上自托管 Typesense 当索引——从 1 万到 100 万唯一不换的那块
  • 列表文档瘦身到 SkillCard,审计入对象存储引用

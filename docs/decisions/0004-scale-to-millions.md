# ADR 0004 — 走向百万级:源/服务解耦 + 分页 + 托管搜索
- 日期:2026-07-04
- 状态:已采纳(方向);分四阶段落地,尚未开工

## 背景
目标目录规模从当前 ~6k 奔几十万到百万 skill。现状三根柱子到 1–5 万条会同时塌:**Git 当存储**(百万小文件,clone/status 爬)、**静态导出**(全量预渲染,构建 OOM,99% 页无人看)、**客户端全量索引**(百万文档索引几百 MB,首屏判死)。前端 `/browse` 现在把 5,811 条全塞客户端整表渲染已经卡——但那只是症状,根因是"把整个目录下发到浏览器再 filter"这套架构不随规模扩展。

## 决策
- **不变量**:catalog(Git)是唯一事实源与公开审计账本,不是请求路径;前端只经 `search(query,filters,page)` 与 `getSkill(id)` 两个入口取数,背后实现逐阶替换;永不把目录下发客户端、永不全量预渲染;采集幂等增量、按 `content_hash` 缓存审计;信任靠 L1/L2/L3 自动化扩展、人工只碰长尾。
- **分页而非虚拟化**:分页解决"别把 N 条传到浏览器"(规模刚需,已在 `search` 缝里),虚拟化只解决渲染;每页 ~30 条时 DOM 天然小,不必叠虚拟化。数字页码可深链 / SEO / CDN 缓存,契合商店;深翻用 cursor·`search_after` 避深 offset。
- **四阶段(阈值门控)**:P0 现~6k 止血 + 焊 `search()/getSkill()` 缝(分页、瘦 payload 到 `SkillCard`、修 `data.ts` 的 O(n²) 重扫);P1 ~1–2 万抽自托管 Typesense 当搜索;P2 ~5–10 万引 Postgres + 对象存储、详情页转 ISR、退 `output:"export"`、管线增量;P3 10⁵→10⁶ 向量语义搜索 / 质量分排序 / 规模化信任 / 成本控制。
- **选型**:搜索 Typesense(自托管,现在就当索引用,从 1 万到 100 万唯一不换的件);服务库 Postgres;向量 pgvector→专用;对象存储 R2/S3;Git 仅留审计账本。

## 后果 / 约束
- P2 起有意识退役"纯静态随处部署"——服务层换 DB,Git 保留为公开账本。
- 真正的硬问题是发现/排序、规模化信任、采集成本、Git 文件天花板,**不是渲染**。

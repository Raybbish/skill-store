# ADR 0008 — M1×P2 合并判据:Postgres 的触发器是用户数据,不是账号
- 日期:2026-07-04
- 状态:已采纳
- 承接:[0004 走向百万级](0004-scale-to-millions.md) 的 P2 阶段、[0001 信任原生社区](0001-trust-native-community.md) 的 M1 最小切片

## 背景
P2(Postgres + 退静态)原触发条件全部是规模阈值(目录 >5 万 / build >30 分钟 / Git 变慢)。M1 账号层引出新问题:有账号是否就必须上 Postgres?讨论结论:

1. catalog 是**可重建的衍生数据**(source of truth 在仓库 + 管线),迁移 ≈ 给管线换输出目标 + 写一个 loader,没有用户数据要搬——「早上库省一次迁移」不成立,provisional schema 反而多一次 v1→v2 带库迁移;
2. M1 最小切片本身不依赖 Postgres:身份可租(GitHub OAuth)、认领可走 git(PR + CI 验证仓库所有权,公开可审计)、收藏是 KV 级轻状态;
3. 真正非 Postgres 不可的是**关系型用户生成内容**(评论/评分/通知/带历史的审计状态)——那是 M2 的范围;
4. 但若 M1 与 P2 时间上贴着,拆开做要付两套胶水 + 一次小迁移,不如一步到位。

## 决策
- **合并线:M1 账号层与 P2 排期间隔 < 1 季度 → 合并为一役。** 管托管 Postgres(现有 Supabase 平滑演进)一库两用:用户状态 + catalog 服务库,跳过 KV/Turso 中间态。
- **回退线:M1 延期超过 1 季度 → 自动退回解耦方案**(OAuth 租用 + git 认领 + KV 收藏),P2 回归规模阈值触发。合并是排期决策,不是架构承诺。
- **范围红线:M1 若出现在设计评论/评分表,先按 M2 范围爬升处理(砍范围),再谈选型。**

## 后果 / 约束
1. **焊缝宪法不因合并松动**:前端只认 `search()/getSkill()`,Postgres 是 source of truth、Typesense 是索引;任何页面直连 SQL 即破缝。
2. **认领永远 git 为凭证、库为索引**——公开可审计的认领记录是信任产品的一部分,不是没数据库时的将就。
3. **P0(分页 + 焊缝)不被合并吸走,仍最先**;P1 Typesense 索引源无所谓 JSON 还是库。
4. 落地计划触发表已同步加入本判据(Desktop:skill-store-百万级落地计划.html)。

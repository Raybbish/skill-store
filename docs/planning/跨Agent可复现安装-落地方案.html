0执行摘要

当前 CLI 已有逐文件复算 content_hash 的完整性校验,但尚未形成真正的跨 Agent、可复现安装:

  • 网页承诺自动探测 .claude / .codex / .cursor,CLI 的探测循环实际为空,默认始终写入 ~/.claude/skills;
  • 在线安装重新浅克隆上游最新 HEAD,没有按 catalog 记录的 upstream_commit 获取内容;
  • 落盘目录只取 skill 名,同名不同来源可能碰撞;
  • 复制到目标目录不是事务操作,既有目录、部分失败和回滚没有明确语义;
  • 平台差异目前只被当成目录差异,尚未表达 frontmatter、调用方式、工具权限和版本差异。

本方案将安装链拆成四层:

flowchart LR
  A["Catalog 元数据\nsource content_hash + upstream_commit"] --> B["Artifact Resolver\n镜像制品或 pinned upstream"]
  B --> C["Adapter\n探测 + 校验 + 目标投影"]
  C --> D["Install Transaction\n暂存 + 复算 + 原子替换 + 回滚"]
  D --> E["Claude / Codex / Cursor\nQwen / Kimi / Comate / CodeBuddy / iFlow"]
  D --> F["本机安装账本\nagent + scope + hashes + adapter version"]

P0 的交付不是“把更多目录写进数组”,而是:

  1. 每次安装明确知道目标 Agent 与作用域;
  2. 获取的内容严格锚定 upstream_commit / content_hash;
  3. 不静默选平台、不静默覆盖、不用最新 HEAD 兜底;
  4. 国内外平台通过同一 Adapter 契约接入;
  5. 原始包与平台投影分别记账,跨平台适配不破坏原始哈希语义。

1背景与当前问题

1.1 承诺与实现不一致

当前网页文案称安装器会自动探测 .claude / .codex / .cursor,见 packages/web/lib/i18n/index.ts;但 detectAgentDir() 的循环没有检测逻辑,最后固定回落 ~/.claude/skills。

这会产生两类直接问题:

  • Codex、Cursor 以及国内 Agent 用户看到“安装成功”,实际文件落在 Claude 目录;
  • 产品最核心的“诚实、可验证”口径被安装入口自身破坏。

1.2 哈希是漂移报警器,还不是可复现安装器

在线 fetchReport() 没有把数据库已有的 upstream_commit 带回 CLI;获取内容时执行 git clone --depth 1 拉取当前 HEAD。上游在收录后只要更新,CLI 就会因哈希不同拒装。

拒装比盲装好,但它只能证明“今天的上游已不是货架版本”,不能让用户安装货架记录的版本。目标应升级为:

给定 skill_id + source_content_hash,任何时刻都获取同一份内容;无法获取时明确失败,绝不悄悄退回最新版本。

1.3 安装身份、目录名与内容身份混在一起

当前目标目录是 id 最后一段。owner-a/repo-a/review 与 owner-b/repo-b/review 会争用同一目录。现有 cp(..., {recursive:true}) 对既有目录也缺少“升级、覆盖、冲突”的区分。

需要把以下身份拆开:

  • skill_id:catalog 三段式作品身份;
  • source_content_hash:上游原始 Skill 内容身份;
  • agent_id:目标宿主身份;
  • scope:用户级或项目级;
  • destination:本次真实落盘路径;
  • projection_hash:Adapter 变换后的安装内容身份;
  • adapter_version:产生该投影的规则版本。

2目标与非目标

2.1 P0 目标

  • 支持 --agent、--scope、--to 三种明确选址方式;
  • 提供可解释的 auto 探测,覆盖多个已安装 Agent 时要求选择;
  • 第一批覆盖 Claude、Codex、Cursor、Qwen Code、Kimi Code、百度 Comate;
  • 紧随批覆盖腾讯 CodeBuddy、iFlow CLI;
  • mirrored 条目优先安装以内容哈希寻址的不可变制品;
  • indexed / 镜像不完整条目按 upstream_commit 从上游获取;
  • 安装前后复算 source_content_hash 或 projection_hash;
  • 目录冲突默认失败,更新和替换有显式语义;
  • 写入目标目录采用暂存、校验、原子替换、失败回滚;
  • add / list / remove / verify 都理解 Agent 与 scope;
  • 网页文案、CLI --help、安装脚本与真实行为一致;
  • 为所有关键路径补单元、集成和 CLI 端到端测试。

2.2 P0 非目标

  • 不构建在线可视化编排器;
  • 不承诺“所有 Skill 在所有 Agent 上效果一致”;
  • 不在安装阶段执行 Skill 自带脚本或依赖安装脚本;
  • 不恢复已下架的安全扫描徽章或“权限营养标签”;
  • 不开放第三方动态 Adapter 代码执行;P0 Adapter 全部随 CLI 发布并接受仓库审查;
  • 不为没有公开稳定安装契约的平台猜测隐藏目录;
  • 不在 P0 修改上游 SKILL.md;目标投影机制先定义,实际变换后置。

3平台范围与接入顺序

平台路径与能力会变化。Adapter manifest 必须保存 docs_url、last_verified_at 和 adapter_version,不能把下表当成永恒常量。

波次 Agent 用户级目录 项目级目录 P0 接入方式 官方依据

补充约束:

  • Kimi 新旧 CLI 的品牌目录不同,用户目录还跟随 $KIMI_CODE_HOME,且 config.toml 可通过 extra_skill_dirs 增加目录;必须按环境变量、配置与版本族探测,不能只保留一个 kimi 路径常量;
  • Comate 可直接读取包括 .claude/skills/ 在内的多家兼容目录。探测时必须区分“已有副本可被 Comate 读取”和“应写入 Comate 自有目录”,默认不为同一 Skill 重复复制;这也使 Comate 自有 Adapter 的实施优先级低于不兼容共享目录的平台;
  • .agents/skills/ 只用于官方明确支持它的平台,不能把它当成所有 Agent 的万能目录;
  • TRAE、WorkBuddy、Qoder 等进入“研究队列”;拿到稳定的目录、ZIP 导入或 API 契约后再接入;
  • 不支持文件目录的产品使用 package-import 或 api 类型 Adapter,不伪装成本地目录安装。

4.2 职责红线

  • Catalog Client 只负责拿事实,不决定安装路径;
  • Artifact Resolver 只负责拿到指定内容,不决定目标 Agent;
  • Adapter 只负责探测、校验和确定目标投影,不直接执行安装事务;
  • Install Transaction 只操作本地文件和账本,不解释平台规则;
  • 回执失败永远不能让安装失败;
  • Adapter 不得执行 Skill 自带代码。

5不可变制品与双哈希模型

5.1 原始内容哈希

现有 meta.content_hash 保持不变,在新代码里明确命名为 source_content_hash。它继续表示上游 Skill 目录内排序后的 (relative path, git blob sha) 集合。

哈希输入规则必须收敛到唯一的 core/content-hash.ts,采集端、CLI、制品构建和 Adapter 投影共同调用或用同一组跨语言 fixture 验证。遍历时沿用现有语义:路径规范化并排序,忽略 .git/,并无条件排除本店注入的保留文件 LICENSE.upstream。该排除规则同样适用于 projection_hash,避免许可证证据文件影响作品身份。

LICENSE.upstream 可以进入分发制品,但不属于 source/projection 内容哈希的覆盖范围;它属于 artifact_sha256 的覆盖范围。三处实现若对这条规则不一致,构建必须失败。

这仍是 catalog 的作品锚,不能因目标 Agent 不同而变化。catalog 返回的 content_hash 缺失、空值或格式非法时,CLI 必须在下载和写盘前以退出码 4 拒绝安装;不得沿用现有 if (content_hash && ...) 的条件校验,也不提供 --force 或隐式降级绕过。--from-dir 等本地入口必须由 fixture manifest 或显式 --expected-hash 提供期望值,不能把“现场算出的值”同时当期望值和校验结果。

5.2 平台投影哈希

如果未来某个 Adapter 必须修改 frontmatter、生成 wrapper 或调整目录结构,安装结果不再等于原始包。此时新增:

projection_hash = hash(project(source_package, agent_id, adapter_version))

规则:

  • source_content_hash 永远指原始包;
  • projection_hash 指真实安装内容;
  • 未发生变换时两者相等;
  • 回执和本机账本同时保存两者;
  • verify 对原样安装校验 source hash,对投影安装校验 projection hash;
  • UI 不得把投影包写成“与上游逐字一致”。

P0 Adapter 只做路径选择和兼容性校验,不修改 Skill 内容。因此 P0 大多数安装的两个哈希相同。

5.3 mirrored 条目

当 hosting=mirrored 且 mirror_complete=true 时:

  1. 构建期从 mirror/ 生成确定性 .skill;
  2. zip 条目排序,固定时间戳、权限和压缩参数;
  3. URL 使用制品字节哈希寻址:/artifacts/sha256/<artifact_sha256 hex>.skill,不得以 source_content_hash 猜 URL;
  4. CDN 设置 Cache-Control: public, max-age=31536000, immutable;
  5. CLI 解包后复算 source_content_hash,不能只信 zip 文件名;
  6. CLI 下载后先校验整个 .skill 的 artifact_sha256,解包后再校验排除 LICENSE.upstream 的 source_content_hash;
  7. 构建清单列出 skill_id / source_content_hash / artifact_sha256 / size / hash_policy,并由制品索引建立 source hash 到 artifact hash 的映射;
  8. 预期制品缺失时构建响亮失败,不能静默跳过。

mirror_complete=false 时不得把残缺镜像作为可复现制品,应走 pinned upstream。

5.4 indexed 或镜像不完整条目

因 licence 不能由本店托管完整内容时,CLI 直接从上游获取 pinned commit:

git init <temp>
git remote add origin <catalog upstream repo>
git fetch --depth 1 origin <upstream_commit>
git checkout --detach FETCH_HEAD
取 catalog upstream 对应 subpath
复算 source_content_hash

严禁:

  • 回退到默认分支 HEAD;
  • commit 获取失败后安装“最接近的新版本”;
  • 使用未经 catalog 约束的用户 URL;
  • 把 indexed 内容经本店 CDN 二次分发。

未来支持非 GitHub 源时,新增 UpstreamResolver,不把 GitHub URL 正则散落到命令逻辑里。

6Agent Adapter 契约

6.1 类型

type AgentScope = "user" | "project";
type CompatibilityStatus =
  | "native"
  | "compatible"
  | "adapted"
  | "warning"
  | "incompatible"
  | "unknown";

interface PathResolverSpec {
  kind: "literal" | "env-home" | "config-array" | "git-root";
  scope: AgentScope | "both";
  value?: string;            // 支持 ${home} / ${projectRoot}
  env?: string;              // 例如 KIMI_CODE_HOME
  fallback?: string;
  configFile?: string;       // 支持环境变量展开
  key?: string;              // 例如 extra_skill_dirs
}

interface AgentAdapterManifest {
  id: string;
  displayName: string;
  aliases: string[];
  adapterVersion: string;
  maturity: "stable" | "beta" | "experimental";
  docsUrl: string;
  lastVerifiedAt: string;
  pathResolvers: PathResolverSpec[];
  markers: {
    commands?: string[];
    configPaths?: string[];
    projectPaths?: string[];
  };
  formatProfile: string;
}

interface AgentAdapter {
  manifest: AgentAdapterManifest;
  detect(ctx: DetectContext): Promise<AgentDetection[]>;
  resolveDestination(ctx: DestinationContext): Promise<string>;
  validate(pkg: SkillPackage): Promise<CompatibilityReport>;
  project?(pkg: SkillPackage): Promise<ProjectedPackage>;
}

安装、删除、回滚不放进 Adapter。这样新增平台不会复制一套危险的文件操作代码。

6.2 声明式优先

路径、环境变量展开、配置数组、Git 项目根、命令 marker 和基础格式规则优先用 JSON manifest 表达。Kimi 先解析 $KIMI_CODE_HOME(缺失时回退 ~/.kimi-code),再读取 config.toml 的 extra_skill_dirs;配置中的相对路径以配置文件约定的基准解析,所有候选路径先规范化、去重再进入探测。只有以下情况才允许 special/*.ts:

  • 目录由配置文件动态决定;
  • 同一平台存在需要迁移的版本族;
  • 平台要求导入包或调用本地 API;
  • 需要确定性生成目标投影。

P0 不加载仓外 Adapter,避免安装器自身成为新的供应链入口。

6.3 兼容性不是“目录存在”

Adapter 的 validate() 至少检查:

  • SKILL.md 是否存在且可解析;
  • name、description 是否满足目标平台约束;
  • 文件夹名是否必须等于 frontmatter name;
  • 平台是否理解 Skill 使用的扩展字段;
  • scripts / references / assets 是否保持相对路径可达;
  • Skill 声明的命令、运行时、MCP 是否在目标环境可用;
  • 是否存在平台明确不支持的调用模式。

P0 对无法确认的能力返回 warning 或 unknown,不得伪造绿色“兼容”。incompatible 必须阻断安装;warning 可由用户确认继续。

7Agent 与作用域探测

7.1 参数优先级

--to
  > --agent + --scope
  > 已保存的同项目偏好
  > auto 探测
  > 明确失败并列出可选命令

--to 保留为最高优先级兼容出口,但仍执行内容哈希和冲突检查。若同时给 --agent,还要执行该 Adapter 的兼容性校验。

7.2 auto 规则

探测信号按可信度排序:

  1. 当前项目已经存在平台目录;
  2. 用户目录已有平台配置或 skill 目录;
  3. 对应 CLI 命令位于 PATH;
  4. 本机安装账本曾成功安装到该平台。

行为:

  • 只命中一个 Agent:选择它;
  • 命中多个 Agent且 TTY 可交互:展示选择器;
  • 命中多个 Agent且非交互:退出并要求 --agent;
  • 一个也未命中:不再默认 Claude,输出支持列表和示例;
  • --yes 只能跳过确认,不能替用户解决平台歧义;
  • --agent all 是显式多装,逐目标独立事务并给汇总结果。

7.3 scope 规则

  • 显式 --scope 永远优先;
  • 当前项目已经存在该 Agent 的项目目录时,auto 可选择 project;
  • 否则默认 user,避免安装命令意外修改 Git 仓库;
  • --scope project 的项目根默认取最近的 .git 祖先,没有 .git 时取 cwd;
  • 提供 --project-root <dir> 覆盖 monorepo / 非 Git 项目边界。

8CLI 用户契约

8.1 命令面

# 查看支持情况和本机探测结果
oh-my-skill agents
oh-my-skill agents --json

# 明确安装
oh-my-skill add owner/repo/skill --agent qwen --scope project
oh-my-skill add owner/repo/skill --agent kimi --scope user

# 自动探测;歧义时要求选择
oh-my-skill add owner/repo/skill --agent auto

# 显式安装到所有已探测 Agent
oh-my-skill add owner/repo/skill --agent all --scope user

# 自定义目录仍保留
oh-my-skill add owner/repo/skill --to /absolute/path

# 查询、验证、移除必须知道目标
oh-my-skill list --agent qwen --scope project
oh-my-skill verify owner/repo/skill --agent qwen --scope project
oh-my-skill remove owner/repo/skill --agent qwen --scope project

8.2 退出码与机器可读输出

退出码 含义
0 全部成功
1 一般错误
2 参数或 Agent/scope 歧义
3 catalog / 网络 / pinned commit 获取失败
4 期望哈希缺失/非法,或 source/projection/artifact 哈希不一致
5 目标不兼容
6 目录冲突或已有内容不可安全替换
7 本地写入或回滚失败
8 --agent all 多目标安装部分成功

--agent all 将每个目标视为独立事务:某个目标失败不回滚已经成功的其他目标,继续执行剩余目标,最后以退出码 8 返回。--json 固定返回 status: "partial"、succeeded[] 与 failed[],每项都包含 agent_id / scope / destination / code / reason。全部成功仍返回 0;全部失败且错误码一致时返回该码,错误码不一致时返回一般错误 1,详细原因仍逐目标保留。P0 不提供跨 Agent 全局原子事务。

所有主要命令支持 --json,返回稳定的 code / message / details,方便模型宿主直接调用 CLI,不必解析人类文案。

8.3 兼容现有用户

  • 现有 --to 不变;
  • 现有 add/list/remove/verify 名称不变;
  • 旧 ~/.oh-my-skill/dirs.json 首次运行迁入新版 state,原文件保留一版周期;
  • 默认 Claude fallback 被视为纠错型 breaking change,在 0.2.0 发布说明中明确;
  • 旧版已安装目录可由 verify --all 发现;只有哈希匹配且身份唯一时才允许“收养”进本机账本。

9安装事务、冲突与回滚

9.1 本机安装账本

账本放在 ~/.oh-my-skill/state.json,不能向 Skill 目录注入平台私有文件,否则会改变内容哈希。

{
  "schema_version": "1",
  "preferences": {},
  "installs": [
    {
      "skill_id": "owner/repo/name",
      "agent_id": "qwen",
      "scope": "project",
      "project_root": "/work/project",
      "destination": "/work/project/.qwen/skills/name",
      "source_content_hash": "sha256:...",
      "projection_hash": "sha256:...",
      "adapter_version": "1.0.0",
      "installed_at": "2026-07-15T00:00:00Z"
    }
  ]
}

账本采用临时文件 + rename 原子更新,并加短时文件锁防止并发 npx 相互覆盖。

9.2 目标目录状态机

状态 默认行为
不存在 正常安装
已由本店管理,同 skill、同 hash 报“已是当前版本”,不写盘
已由本店管理,同 skill、不同 hash 视为更新,确认后事务替换
已由本店管理,不同 skill 同名冲突,失败
目录存在但不在账本 unmanaged,失败;只有显式 --replace 才可替换

P0 不自动给同名 Skill 改名,因为部分平台要求目录名与 frontmatter name 一致。需要同时安装两个同名来源时,先输出冲突说明;P1 再通过确定性目标投影解决命名空间问题。

9.3 文件事务

获取内容到系统临时目录
→ source hash 校验
→ Adapter validate / project
→ projection hash 校验
→ 在目标父目录创建 .<name>.oms-staging-<id>
→ 完整复制并再次复算
→ 既有受管目录 rename 为 backup
→ staging rename 为 destination
→ 原子更新 state
→ 删除 backup

任一步失败:

  • 删除 staging;
  • destination 已换出但新目录未就位时恢复 backup;
  • state 未提交前不发成功回执;
  • 回滚失败使用退出码 7,保留 backup 路径并给出人工恢复命令;
  • 不使用 rm -rf 清理用户未知目录。

10数据与 API 变更

10.1 CLI 所需 catalog 字段

在线查询改为显式 select,至少返回:

id
name
hosting
mirror_complete
license
upstream
upstream_commit
content_hash
delisted_at

现有 skills 表已有 upstream_commit,CLI 只需停止丢弃它。mirror_complete 需要加入 Supabase 投影与 sync preflight。

mirrored 条目的安装查询还必须合并构建产出的 artifact_sha256 / artifact_url / artifact_size。这些是制品构建事实,可来自独立 artifact index 或物化表,不要求伪装成采集元数据;但 CLI 不得用 source_content_hash 自行拼出下载 URL。

退市条目默认拒绝新安装;若本机已有相同 hash,仍允许 verify。

10.2 安装制品清单

构建期先在 packages/web/out/artifacts/ 暂存并验证,再上传到支持不可变对象和生命周期策略的制品存储/CDN:

/artifacts/sha256/<artifact_sha256 hex>.skill
/artifacts/sha256/<artifact_sha256 hex>.json
/artifacts/index.json

<hex> 写死为 artifact_sha256 去掉 sha256: 前缀后的 64 位十六进制值。artifacts/index.json 以 skill_id + source_content_hash 映射到 artifact_sha256 + artifact_url + size;静态站点输出只是 CI 暂存物,不得作为跨版本保留的唯一事实源。

manifest 示例:

{
  "schema_version": "1",
  "source_content_hash": "sha256:...",
  "artifact_sha256": "sha256:...",
  "size": 12345,
  "created_from": "catalog mirror",
  "deterministic_zip": true,
  "hash_policy": {
    "source_projection_excludes": [".git/**", "LICENSE.upstream"],
    "artifact_covers": "complete .skill bytes"
  }
}

按 artifact hash 寻址的 manifest 只记录由制品字节可推导的稳定事实,不得写入会随收录关系变化的 skill_id 或 subjects[]。Skill 与制品的多对一映射只属于可更新的 artifacts/index.json,否则同一 artifact 被新 subject 复用时会让“不可变” manifest 发生漂移。

覆盖范围必须明确:source_content_hash 与 projection_hash 对规范化后的 Skill 文件集合计算,排除 LICENSE.upstream;artifact_sha256 对最终 .skill 的每一个字节计算,因此覆盖包内的 LICENSE.upstream、文件顺序与 ZIP 元数据。前者回答“作品内容是否相同”,后者回答“下载到的制品是否逐字相同”。

保留策略在 P0 同步冻结:当前 catalog 或灰度版本引用的制品无限期保留;不再被任何发布版本引用的制品保留 180 天,由对象存储生命周期任务清理;下架不等于立即删除,但法律下架、许可证撤回或恶意内容处置可立即 tombstone 并删除。GC 只删除“无引用且超过 180 天”的对象,每次输出删除清单与可审计日志,绝不在 Web build 中顺手清理。监控至少记录对象数、总字节、月新增字节、孤儿对象和 GC 删除量。

10.3 安装回执

保持 ADR 0017 的语义:回执只证明获取渠道或本机持有,不证明使用深度与安全。建议给 install_receipts 增加可空字段:

agent_id
scope
adapter_version
projection_hash

原 content_hash 继续记 source_content_hash,避免历史数据断裂。旧 CLI 不传新字段仍可写入。

10.4 兼容性结果后置

P0 只在本地 preflight 输出兼容性。公开兼容矩阵后续使用独立派生对象,不塞进采集事实 meta:

skill_id + source_content_hash + agent_id + agent_version
+ adapter_version + status + reason_codes + tested_at

作者声明与平台实测必须分开,不能把“支持 Qwen”这种自报字段直接渲染成已验证徽章。

11兼容性原因码

原因码必须稳定,供 CLI JSON、测试和未来 UI 共用:

原因码 含义 默认级别
missing-skill-md 缺少入口文件 incompatible
invalid-frontmatter YAML 或必填字段不合法 incompatible
name-folder-mismatch 目标平台要求名称与目录一致 incompatible
unsupported-frontmatter-field 平台不理解扩展字段 warning
runtime-missing Node/Python/系统命令不可用 warning / incompatible
mcp-missing Skill 依赖的 MCP 不存在 warning
script-execution-unknown 宿主能否执行脚本尚未验证 unknown
adapter-version-stale 平台文档晚于 Adapter 验证时间 warning
platform-version-unsupported 已知宿主版本不在支持范围 incompatible

“目录复制成功”只能说明 installed,不能自动把兼容性标为 compatible。

15可观测性与成功指标

19ADR 0029 冻结裁决

本轮审查补齐的四项不再列为开放问题,应直接作为 ADR 不变量:缺失/非法内容哈希拒装;LICENSE.upstream 不进入 source/projection hash 但进入 artifact hash;--agent all 部分成功返回退出码 8;平台路径只采用正式、稳定文档,无法确认者进入研究队列。Kimi 动态路径、Comate 兼容目录去重和 artifact 保留策略同样写入实现约束。

2026-07-15 已采纳以下三项建议,其余可按本文直接拆任务:

  1. 默认 scope:建议“已存在项目平台目录 → project;否则 user”,避免隐式改仓库;
  2. 多 Agent 行为:建议 TTY 选择、非 TTY 报错;--yes 不解决歧义;
  3. P0 是否允许内容投影:建议不允许,先做原样安装 + 兼容性阻断;双哈希能力保留到 S4。

以上裁决已写入 ADR 0029,作为 CLI、网页安装生成器和未来 Adapter SDK 的共同约束。

M0 详细设计

v1.0 · 2026-07-02 · 上游文档:Skill Store PRD v1.0 · 设计原则:长期最优架构,M0 只做骨架的第一层肉

0目标与范围

M0 交付「可信目录」:500+ 个经过 L1-L3 安全审计、带权限营养标签的 skill,可浏览、可搜索、可一键安装,审计报告公开可验证。周期 4-6 周。

范围内范围外(留给 M1/M2)
采集管线:官方精选仓 + skills.sh 头部榜单两个 source adapter;托管/索引双轨;哈希去重;每日增量同步GitHub 全域索引、第三方 Hub 信号聚合
安全审计 L1(静态签名)L2(脚本分析)L3(LLM 意图审查);风险五因子标签 + 文件级证据;人工复核队列L4 动态沙箱;可复现评测协议(赛道非裁判);效果对比自动产出
商店前端 P0:今日 / 分类搜索 / 榜单(仅安装量榜)/ 详情页(权限标签为主角);全站 SSG可复现评测榜、评论系统、在线试玩、开发者中心
npx CLI:add / list / remove + 安装时哈希校验付费、私有货架、企业功能
M0 详情页的「主角」暂时是权限营养标签 + 安全审计报告(可复现评测 M1 才有)。这决定了 M0 的营销叙事:「第一个把每个 skill 的权限行为讲清楚的目录」——先立信任,再谈质量。

1总体架构

GitHub catalog 仓(事实源) ←(PR)← pipeline workers(采集/审计,GitHub Actions 调度)
catalog 仓 →(增量同步,commit 溯源)→ Postgres(Supabase)→ Next.js 前端(SSG + ISR)+ REST API → npx CLI

四个部件放一个 monorepo,加上独立的 catalog 数据仓:

skillstore/                # monorepo(pnpm workspaces)
├─ packages/
│  ├─ pipeline/            # 采集 + 审计编排(TypeScript)
│  │  ├─ sources/          #   source adapters: official.ts / skills-sh.ts
│  │  ├─ scanners/         #   L1/L2/L3 扫描器适配层(调用容器化扫描工具)
│  │  └─ jobs/             #   ingest / audit / sync 三个入口
│  ├─ web/                 # Next.js 商店前端 + API routes
│  ├─ cli/                 # npx 安装器(npm 包)
│  └─ schemas/             # skill-report JSON Schema、DB 类型(单一来源,四端共享)
└─ .github/workflows/      # ingest.yml / audit.yml / sync.yml

skillstore-catalog/        # 独立数据仓(公开,事实源)
└─ skills/<owner>/<name>/
   ├─ skill-report.json    # 元数据 + 审计结果(所有条目必有)
   └─ mirror/              # 托管型才有:SKILL.md 及资源的镜像副本

为什么这个架构长期对

① catalog 仓公开 = 审计报告天然可被第三方验证,每次变更走 PR 留痕,这是信任产品的地基;② DB 是 catalog 的派生视图(每条记录带 upstream_commit),坏了可全量重建,没有「DB 和仓库不一致」这类长期债;③ M1 加评测只是往 skill-report.json 里加一个 eval 字段 + 一个新 worker,前端加一列,架构零改动;④ 扫描器容器化(见 §4),未来换更强的扫描工具不动编排层。

2技术选型

部件选型理由(长期视角)
编排/前端/CLI 语言TypeScript 单语言四端共享 schemas 包,类型一路贯通;招人/AI 结对都最顺
扫描工具容器化调用(Python 生态:cisco skill-scanner、semgrep、YARA)安全生态在 Python,不迁就语言统一;容器边界=随时可替换
数据库Postgres(Supabase 托管)RLS、PostgREST、全文搜索一站式;规模到了迁自管 PG 无缝
前端Next.js(App Router)+ Vercel/Cloudflareskill 详情页 SSG(SEO 是获客主渠道),增量再生成(ISR)对齐每日同步节奏
搜索M0 用 Postgres FTS;预留 Meilisearch 接口500-5000 条量级 FTS 足够,不提前引入运维负担
调度GitHub Actions(cron + workflow_dispatch)aiskillstore 验证过千级规模可行;M2 量级再迁队列(Temporal/Inngest),编排层已按 job 抽象,迁移面小
L3 模型可插拔(env 配置),默认 Claude + 第二模型抽查交叉单模型审计会被针对性绕过;交叉审计不一致 → 自动进人工队列
CLI 分发npm 公开包npx 零安装体验,与 skills.sh 用户习惯一致

skill-report.json(Schema v1,catalog 仓内每 skill 一份)

    "upstream_commit": "a1b2c3d",               // 同步锚点,每日 diff

DB 侧四张核心表:skills(report 的扁平投影 + FTS 列)、publishers、audit_queue(人工复核工单)、sync_state(每源 adapter 的游标与上次成功 commit)。全部由 packages/schemas 单一来源生成类型。

4采集与审计管线

4.1 ingest(每日 cron)

source adapter 拉清单 → agentskills.io Schema 校验 → licence 探测 → 规范 ID + content_hash → 去重合并(同 hash 并条目、聚合信号)→ 双轨分流(mirrored/indexed)→ 写 catalog 仓分支 → PR「ingest: N skills」

(2026-07-03 校正)起步 adapter:official.ts 读手维护的 sources.yaml(anthropics/skills、vercel-labs/agent-skills 等);skills-sh.ts 解析首页 SSR 榜单(私有 /api/v1 实测 401,故走 HTML 榜单)取 top N(默认 200),按安装量降序。现已扩到 GitHub 全域 topic:claude-skills 采集(github-search.ts)+ awesome 精选信号(hub-signals.ts)。每个 adapter 实现统一接口 discover() → SkillCandidate[]。

4.2 audit(ingest PR 合并后触发 + 每日对过期报告重审)

层M0 实现产出
L1 静态签名YARA + 正则规则集:密钥模式、curl|bash、大段 base64、eval/exec、已知 C2 域名命中即 rejected 或标记证据
L2 脚本分析semgrep 规则:网络调用、路径逃逸(../、家目录)、env 读取、子进程;cisco skill-scanner 容器作为基线风险五因子 present/detail + 文件级证据
L3 LLM 意图审查模型读 SKILL.md 全文 + 脚本摘要,判断指令意图与文档声称是否一致、有无隐藏指令;抽样 20% 用第二模型交叉意图结论;与 L1/L2 或交叉模型矛盾 → needs_review

状态机:pending → pass / needs_review / rejected。含 network 因子的一律至少 needs_review,由人工在 audit_queue 里放行——M0 期人工量可控(预估 <15%),这条规则是「认证恶意数恒为 0」反指标的第一道闸。批处理继承已验证模式:分片并行、单项隔离、指数退避、audited_at 新鲜度截止线(30 天过期重审,上游 commit 变更立即重审)。

4.3 sync(catalog main 分支 push 触发)

diff 上次成功同步的 commit → 变更条目 upsert 进 Postgres(带 --marketplace-commit 溯源)→ 触发前端 ISR 再验证。关键路径分层:sync 硬失败告警;缓存/搜索索引刷新失败仅 warning。

5前端与 CLI

页面(复用交互原型的设计,SSG 全静态)

/ 今日(编辑推荐 + 热门 + 分类)· /browse 分类/搜索/筛选(含「仅无外联且扫描通过」)· /charts 安装量榜(可复现评测榜位留占位,标「M1 上线」制造预期)· /skill/[id] 详情页 · /audit/[id] 审计报告全文(链接到 catalog 仓对应文件,可验证)。详情页布局沿用原型,评测位置 M0 显示「三层审计:通过 ✓」+ 风险因子披露。每页 SSG + 结构化数据(SoftwareApplication schema),SEO 是 M0 主要获客渠道。

npx CLI

# 安装(自动探测 agent:.claude/ .codex/ .cursor/…)
npx skillstore add aideas-labs/slide-craft
# 安装时行为:
# 1. 拉 API 元数据 → 2. mirrored 从 catalog 下载 / indexed 从上游拉取
# 3. 校验 content_hash 与货架一致(防上游被替换的供应链攻击)★M0 就要有
# 4. 展示权限营养标签,含 network/scripts 因子时要求确认 → 5. 落盘对应目录
哈希校验 + 安装前权限确认是 CLI 的灵魂:别家 npx skills add 是盲装,我们的安装动作本身就在传递「这家店不一样」。

6周计划与验收

周目标关键产出
W1骨架monorepo + schemas 包 + catalog 仓建立;official adapter 跑通,首批 ~100 条(官方仓)入 catalog
W2审计 L1/L2规则集 v1 + skill-scanner 容器接入;首批全量出 risk_factors;audit_queue 表与最简复核界面(可先用 GitHub Issue)
W3审计 L3 + 同步LLM 审查 worker(批量/重试/截止线);sync worker + Supabase;skills.sh adapter 上线,货架扩到 500+
W4前端四个页面 SSG 上线,详情页权限标签完整;域名 + Analytics
W5CLI + 收尾npm 包发布(add/list/remove + 哈希校验 + 权限确认);全链路演练:上游改动 → 重审 → 同步 → 前端更新
W6缓冲/打磨规则误报调优、文案合规复查(「已扫描」措辞)、发布首篇内容(「我们审计了 500 个 skill,发现了什么」)

验收标准(退出 M0)

① 500+ skill 上架且权限标签覆盖率 100%;② 审计报告全部公开可访问且与货架一致;③ 每日同步连续 7 天无人工干预跑通;④ CLI 在 Claude Code 与 Codex 两个 agent 真机安装成功;⑤ needs_review 队列处理时长中位数 < 48h;⑥ 全站无一处「保证安全」类措辞。

7成本与关键决策记录

M0 成本量级

基础设施(Supabase/Vercel/GitHub Actions 免费或个位数美元档)近零;主要成本是 L3:按 500-1000 skill、每个 SKILL.md+脚本摘要平均 ~8K token 输入、双模型抽查,首轮全量审计约在数十美元量级,月度增量(新增+过期重审)更低。真正的成本大头在 M1 评测(每 skill 20 任务 × 多次 × 跨模型),M0 不承担。

ADR(决策记录)

决策选择被否方案与原因
事实源公开 Git catalog 仓直接写 DB:丢失可验证性与 PR 留痕,信任产品不可接受
托管策略mirrored/indexed 双轨全托管:licence 风险;全索引:上游可被篡改,无法做哈希校验
语言TS 编排 + 容器化 Python 扫描器全 Python:前端/CLI 生态劣势;全 TS:放弃安全扫描生态
network 因子处理一律人工放行纯自动:ClawHub 漏网教训,M0 信任成本远高于人工成本
搜索Postgres FTS 起步Meilisearch:当前量级纯增负担;接口已预留
调度GitHub Actions 起步自建队列:aiskillstore 证明 GHA 千级够用;编排按 job 抽象保迁移性

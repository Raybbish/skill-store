4curl 形态:萌新友好定夺

你问「哪种对萌新友好」——关键在于两种其实服务不同人群,而 curl 这个入口存在的理由本就是「给没 npx 的人兜底」。

维度纯 shell(构建时内联元数据)薄封装转 npx
真·免 Node✓ 是(切中 curl 入口的存在理由)✗ 仍需 Node/npx——那还不如直接用 npx 入口
运行时依赖curl + git + sha256sum/shasum;免 jq(元数据 build 时内联,无需解析 JSON)Node / npx
Windows✗ 需 sh(Git-Bash/WSL)✓ 跨平台
错误友好度预检 curl/git/sha256 缺失即给友好提示;权限已预渲染✓ 复用 CLI 成熟错误信息
逻辑单一来源脚本模板与 CLI 两处维护(但都薄)✓ 只有 CLI 一处
萌新体验一行 curl、无需装 Node、权限已列好、只在缺 git 时提示要先有 Node;有则最省心
已定:纯 shell + 构建时内联元数据(curl 是兜底、非主路)。破局点是——脚本既然是构建时按 skill 生成的,就把权限标签、文件清单、content_hash 全部内联进脚本,运行时不再需要 jq。于是纯 shell 版既保住「真免 Node」的定位,又对萌新友好:一行 curl、权限已预渲染、/dev/tty 读确认、git hash-object 复算 blob sha + sha256sum 校验,预检缺失依赖给人话提示。Windows 萌新走 npx 那条——两个入口互补,不是二选一。

备注:既然安装体验已定为「npx 主推、curl 兜底」,curl 就必须是纯 shell——薄封装转 npx 仍要 Node,对「没 Node 的人」等于没用,已排除。

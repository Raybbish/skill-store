社区层设计 v2 —— 对象锚定与隐形验证

结构上像豆瓣,不像论坛:社区是挂在条目上的四种内容类型,不是四个板块。验证藏在安装动作里,用户永远不见「请验证」。

关联:ADR 0001(信任原生社区,实现层由本稿修订)· ADR 0006(一键认领)· ADR 0013(微文案三来源)· ADR 0014(场景包)

0 · 定位前提(与 v1 的差异)

2026-07-06 重定位后,本稿全部推导基于此

不以「卖信任」为主叙事。安全检查降级为小功能(卫生标准:content_hash 校验静默保留,verdict 服务冻结在 flag off,ADR 0011/0012),因为不成熟的扫描卖不了任何信任。主动打造的是活人感:真实的人、真实的产物、真实的更新,出现在货架上。

由此推出三条设计公理:

验证要隐形参照 App Store:「已验证」不是步骤,是获取渠道本身。用户从头到尾不知道有验证这回事。
内容挂对象参照豆瓣:评论/求助/笔记全部锚在条目(skill/作者/包)上,不存在脱离对象的帖子流。
零回复自价值每种内容类型在零回复时对发帖人自己必须有价值,否则冷启动期就是空板块。

1 · 七平台参照 —— 各偷一件事

平台偷什么落到我们
豆瓣 ⭐条目中心:评论/评分/清单全挂条目;豆列skill=条目,社区的家在详情页;豆列=开放期社区清单(ADR 0014 三阶段)
知乎问答是沉淀资产,可被搜索引擎索引求助绑 skill+版本,已解决问题=该 skill 使用知识库+SEO 入口;邀请回答路由给认领作者
小红书内容单元=带真实产物的笔记用法笔记:截图/生成文件/跑过的命令,「我用它做成了什么」,活人感浓度最高
Reddit社区围绕实践不围绕产品;投票投内容不投人不按 skill 建子版(必空),按场景聚合;早期只要「有用」计数,不做 downvote
推特关注=订阅原语;build in public关注作者/skill 得更新流;开发者说=git release 自动成帖+作者加注(供给侧活人感免费拿)
Instagram作者页=作品集视觉产出类 skill(pptx/design/video)配产物画廊
OnlyFans卖关系不卖文件与 C2C 证伪结论一致;免费承诺期只留钩子(作者页 GitHub Sponsors 直链,零抽成零基建);付费墙杀 SEO,不做

2 · 结构 —— 四种内容类型,不是四个板块

原型里的四板块(求助台/晒用法/评测挑战/公告复盘)重构为:
内容类型参照锚点零回复自价值排期
短评豆瓣短评skill 详情页「已验证安装」的公开使用记录M1
求助 Q&A知乎skill 详情页(绑版本)求助记录本身+SEO 页面M1
开发者说推特/TapTap作者页+skill 详情页作者的 changelog(自动生成可加注)M1
用法笔记小红书/Insskill 详情页+作者页+包页发帖人的作品展示M2
评测挑战独有skill 详情页评测区挑战记录=复现报告M3(等评测线真实跑通)

「公告&复盘」拆出社区——那是商店自己的声音,做成官方 blog/changelog(build in public 的载体),不占社区心智。

/community 聚合页最后建:它只是上述对象上内容的聚合流。密度门槛:周新帖 > 20 才开页面;在此之前导航不出现「社区」入口。现有 demo threads(lib/community.ts 演示数据)不上线——空板块+假数据是活人感的反面。

3 · 「已验证安装才可评」—— 隐形验证机制

目标用户包含大量不会用 GitHub/终端的人;原则:验证藏在安装动作里

3.1 先认清边界

skill 文件公开、安装免费且发生在本地,密码学上无法证明安装(不装也能算哈希)。所以机制目标是:服务端留痕 + 提高刷评成本 + 措辞诚实,不是「证明」。

3.2 回执的三个来源,按用户能力分层

路径用户动作回执产生面向
① .skill 下载(主)网页点「安装」→ 下载 .skill → 拖进 Claude下载发生在服务端,天然回执 (会话/账号, skill_id, content_hash, channel=download)不会终端的大多数;Cowork 型用户唯一现实路径
② 命令带 token(次)点「复制安装命令」→ 粘贴运行命令即 npx oh-my-skill add pptx --t 8f3k,CLI 装完(哈希校验过)带 token 回传,自动绑到生成命令的网页会话会用终端的;免 login、免 device flow
③ 补验(兜底)评价框提示运行 verify 命令npx oh-my-skill verify owner/repo/name --code ABC:本地找到 skill 目录、复算哈希对上 content_hash、带短码提交回执手动拷贝/其他渠道装的;挡住「装都没装」的最懒刷评

3.3 账号:邮箱验证码 + 延迟注册

浏览、下载不要求登录(回执先挂匿名会话);只在按下「写评价」那一刻要邮箱验证码(Supabase Auth email OTP),登录后把该会话的回执并入账号。GitHub OAuth 降级为开发者可选项。用户感知只有「评价前输个验证码」。

3.4 评价 UX:豆瓣短评,不是知乎长文

点选「好用 / 一般 / 不好用」+ 可选一句话「它帮我做成了什么」+ 可点场景词 chip(接微文案词表,ADR 0013)。打字可选,点两下就是一条有效评价。评价行绑定回执里的 content_hash:徽章显示「评于 v3」;目录哈希已更新的显示「评于旧版本」。一人一 skill 一评,换大版本可追评。

3.5 反刷 = 权重,不是门槛

  • 冷却期下载/安装后 24h 才能评
  • 限频单设备/IP 限频;邮箱账号龄与行为做先验
  • 进榜权重榜单评分只算「有回执 + 有账号龄」的评价;刷子能发评,撬不动分数
  • 利益回避认领作者不可评自己的 skill(对 claimed publisher 匹配)

诚实认账:邮箱账号的 sybil 成本远低于 GitHub 账号。本方案在当前规模够用;规模化信任升级留给 P3(与 [走向百万级] 对齐)。

3.6 徽章措辞红线

徽章写「从本店安装」,tooltip 写清验证的是获取渠道(经本店下载/CLI 哈希校验),不是使用深度,更不是安全背书。全站沿用「不说保证安全」的既有红线。

3.7 副产品:自有装机量

回执匿名聚合 = 自己的装机量信号(App Store 模式),发现排序的燃料自产,摆脱对 skills.sh 榜单的依赖。可先于账号层上线:CLI 首跑生成 machine-id 匿名计数,首跑明示、--no-telemetry 可关;登录后 machine-id 回执并入账号。

4 · 数据模型(沿用 M0 预留,不改表结构)

install_receipts: { id, user_id?, session_id?, machine_id?, skill_id, content_hash,
                    channel: download|cli|verify, cli_version?, created_at }
reviews:          { id, user_id, skill_id, receipt_id, content_hash_at_install,
                    verdict: good|ok|bad, text?, scene_tags[], created_at }
                  UNIQUE(user_id, skill_id)   -- 换大版本追评另行放开
threads/comments: M0 预留 schema(skill_id + version + verified_install)原样够用

RLS:回执只能插自己的、读自己的;聚合计数走服务端视图。评论/评分是「第一条不可重建的关系型用户数据」——命中 ADR 0008 的 M1×P2 合并判据,与 Postgres 选型同批落。

5 · 排期

里程碑内容
M1短评(隐形验证全链路:.skill 下载回执 + token 命令 + 邮箱 OTP 延迟注册)+ 求助 Q&A 挂详情页 + 开发者说 + 作者认领入口(ADR 0006 提前,活人感定位下价值上升)
M2用法笔记(带产物)+ 社区清单(豆列,接 ADR 0014 开放期)+ /community 聚合流(密度门槛达标后)+ 关注/订阅
M3评测挑战(评测线真实跑通为前置)+ 委托/打赏钩子(Sponsors 直链)

工程排序的真话:整套验证依赖「经我们渠道安装」是主流路径。第一优先级是把「下载 .skill 拖进 Claude」修得丝滑——验证系统是它的免费副产品,不是反过来。

6 · 红线汇总

  • 不装活demo threads 不上线;空板块即砍;机器写的标机器、人写的署名(对齐 ADR 0015「不把估算伪装成真实」)
  • 不越语义「从本店安装」只claims获取渠道;不说「保证安全」
  • 不建空壳/community 聚合页密度门控;不按 skill 建子版
  • 不收费M0-M1 全免费承诺不破;OnlyFans 机制只留 Sponsors 钩子
  • 零内部词汇货架文案红线沿用(ADR 0014):审计/采样/上游等词不出现在社区 UI
